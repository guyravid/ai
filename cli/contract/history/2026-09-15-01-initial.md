# 1.0 — Initial contract

## Summary

Established the contract for command-line tools that give an automated agent access to a remote API.
It covers output streams, the response envelope, a fifteen-code error taxonomy bound to exit codes,
dotted command naming, tiered discovery and `teach`, the `doctor` and `list-config` diagnostics,
context discipline (field projection, size caps, empty-stripping, time windows), paging that fills
`--limit` inside the tool, locally stored datasets, gated writes, secret handling, a seven-tier
configuration model with profiles, determinism, human-readable output, optional MCP server mode over
stdio and HTTP, reserved names, and versioning rules.

The document was drafted, reviewed against a comparable specification, and reworked before its
first commit. This entry records the state it was first committed in.

## Changes

- **Added** §0–§1 — terminology and six axioms from which every rule is derived.
- **Added** §2 Output streams — one document per invocation, written in one piece; errors on stdout;
  no ANSI, stdin, or prompting; four named exceptions.
- **Added** §3 The envelope — `ok`, `tool`, `command`, `data`, `error`, `meta`; paging state in
  `meta.page`; nothing time- or request-specific without `--timing`.
- **Added** §4 Error codes — fifteen codes with fixed exit codes, a tool-specific range, and a
  `cache_miss` code distinct from `not_found`.
- **Added** §5 Command naming — dotted names that map directly onto the command line.
- **Added** §6 Discovery — `tools` (names), `tools --detail`, `describe` in MCP tool shape with an
  output schema; a tiered `teach` whose orientation points to `teach contract`; generated `flags`
  and `config` topics; a fixed `--help` ending.
- **Added** §7 Diagnostics — `doctor` with ordered checks and a `skip` status; `list-config` with
  exact provenance for every setting.
- **Added** §8 Context discipline — defaults, `--fields`, empty-stripping, byte and string caps with
  record-level truncation, and time windows with strict formats.
- **Added** §9 Paging — the tool follows upstream pages to fill `--limit`; one `meta.page` shape;
  self-sufficient cursors.
- **Added** §10 Datasets — `--all` stores a projected JSON Lines file and returns its path; `dataset`
  commands; sliding lifetime; failure when the directory is unusable.
- **Added** §11 Writes — `write` prefix, `--confirm` with preview, `--dry-run`, read-only builds, no
  automatic write retries.
- **Added** §12 Secrets — credential resolution order, forbidden credential flags, a redactor
  covering encoded forms and prefixes, owner-only credential files.
- **Added** §13 Configuration — platform directories, automatic config loading, seven precedence
  tiers resolved per setting, profile-last variable names, a JSON config file that may not hold a
  credential value.
- **Added** §14 Determinism, §15 `--human`, §16 MCP server mode, §17 reserved names, §18 versioning.
- **Added** §16.1 — a build with server mode remains a complete command-line tool; server mode is
  entered only through `serve`.
- **Added** §16.3 — a remote listener requires a token and TLS: either served by the tool from a
  certificate and key, or declared as terminated upstream with `--tls-terminated-upstream`.

## Rationale

**Why a contract at all.** An agent needing API data would otherwise hold the API key in its own
context, where transcripts and shell history keep it. A local tool holding the key in its own
environment removes that exposure. A fixed interface across all such tools means an agent that has
learned one has learned them all.

**Why paging state moved into `meta`.** With the tool filling `--limit` itself and whole result sets
handled by the `dataset` commands, a separate top-level paging object had no remaining purpose.
Grouping it as `meta.page` keeps every fact about the response in one place.

**Why the tool pages internally.** An agent asking for sixty records should get sixty in one call. A
tool that returned one upstream page per call would turn every request into several turns.

**Why datasets fail rather than degrade.** An unusable dataset directory could be worked around by
returning a single page, but the agent asked for the whole set, and a silent partial answer is worse
than a clear configuration error.

**Why `cache_miss` is its own code.** An expired dataset is fixed by re-running the query that built
it; a missing upstream record cannot be fixed at all. One code for both would hide which applies.

**Why `--human` is available everywhere.** Operators read the same commands agents do. Keeping JSON
as the unconditional default, and never enabling `--human` automatically, preserves the agent's
guarantees while letting a person read any output.

**Why the config file loads automatically.** Configuration belongs to the tool, not to each command
line. A known default location, overridable by flag or environment variable, means an operator
configures a tool once.

**Why the config file may not hold a credential value.** The file will be read by people and agents,
pasted into bug reports, and committed by accident. Rejecting a credential value at startup makes the
file safe by construction instead of by convention.

**Why environment variables outrank both the file and file-based credentials.** They are the easiest
thing for a deployment to change, so a deployment can always override what it does not own.

**Why a remote listener cannot run in plaintext by default.** A bearer token sent over plain HTTP can
be read by anyone on the network path and replayed, which would make the authentication meaningless.
An earlier draft allowed remote plaintext with only a warning; review found that a warning is not a
control. Banning remote binds outright would break containers, where a published port requires a
non-loopback bind and TLS is commonly terminated by an ingress or mesh. Requiring either the tool's
own TLS or an explicit, named declaration that TLS is handled in front keeps both deployments possible
while making plaintext a recorded decision instead of the default.

**What was deliberately left out.** Upstream retry and backoff policy is a per-tool decision; the
contract requires only that the final outcome carries the right error code. Packaging requirements
belong to implementation guidance, not to observable behaviour. Numbered conformance checks live
with the test tooling, derived from this document.
